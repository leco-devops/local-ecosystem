CI/CD

Push to a repository, LEco redeploys the app. Each pipeline runs pull → build hook (optional) → deploy → verify → record. Verify is a real HTTP probe of the app's public URL, so a deploy that leaves the app returning 502 is recorded as a failed run, not a successful one. Every run is kept with its commit, per-step status and captured log, which is also what makes rollback possible.

1 · Pipelines

One pipeline per application. The webhook URL goes into the Git host (GitHub → Settings → Webhooks, GitLab → Settings → Webhooks); the secret is generated here and shown once.

The build/test hook is a compose service the application itself declares — LEco runs docker compose run --rm --no-deps <service> with no command override, so the command lives in the app's own compose file (add it in docker-compose.leco-hosting.yml to leave the upstream repo untouched). Arbitrary shell commands are deliberately not accepted: this config is reachable from an internet-facing webhook, and a command string there would be host-level remote code execution.

4 · What rollback does and does not cover

  • Covers: re-checkout of the previously deployed commit and a full redeploy of the app's compose project, followed by the same verify probe. The run is recorded like any other.
  • Does not cover: database schema and data. A migration that ran on the way forward is not reversed — old code against a new schema can fail in ways a green verify probe will not catch.
  • Does not cover: volumes, uploaded files, caches, queues, or anything written by the release being rolled back; nor changes made outside the repository (env files, secrets, Traefik edits).
  • Rollback target: the SHA recorded as deployed before the current one. It exists only after this pipeline has deployed at least twice.
