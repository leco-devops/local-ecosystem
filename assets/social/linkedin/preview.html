Deploy first.Configure never.

Inside LEco DevOps — an open-source local cloud edge for the apps you already have.

MITv0.3.0Docker · Traefik65 MCP tools~7 min read

Draft for LinkedIn · Rajneesh Maurya · github.com/leco-devops/local-ecosystem

Every team I have worked with has the same folder on someone's laptop: a README with eleven setup steps, four of which are wrong, and a comment near the bottom that says “ask Priya about the ports.”

We accept this. We accept that the app runs on localhost:3000 locally and behind a real hostname in production, that cookies and CORS behave differently in each, that a new hire loses two days to a port conflict, and that “works on my machine” is a joke instead of a bug report.

LEco DevOps is our attempt to delete that gap. It is a free, MIT-licensed local cloud edge: point it at a repository, and it reads what you already built, converts it into platform manifests, wires Traefik and Docker Compose, and serves your app on a real hostname with TLS your browser trusts — https://myapp.lh instead of http://localhost:3000.

The USP: it reads your repo instead of asking you to rewrite it

Most platforms ask you to adopt them. You write their YAML, restructure your services, learn their abstractions — and then you find out whether it works.

LEco inverts that. Read → Convert → Orchestrate → Deploy.

It scans docker-compose.yml (including monorepos that hide it in infra/, deploy/, ops/ or .docker/), every wrangler.toml / .json / .jsonc in the workspace, .env files, Dockerfiles and declared port tables. Then it writes the platform wiring beside your repository, never inside it: a bridge manifest, a profile, a Compose overlay that joins the shared network, a Traefik fragment, and a registry row. Your checkout keeps a symlink and nothing else — pull, branch, or delete it, and LEco leaves no residue.

One rule underpins the whole thing, and it is the rule most tools quietly break:

Ports come from evidence, never from invention.

Every port must trace back to a Compose port pair or a declared port table in a named file. If the evidence does not say which port a component listens on, LEco lists it under unknowns and asks. A plausible-looking guess produces a stack that builds, starts, and serves nothing — and it reads as an application bug for hours. We would rather stop and ask.

That discipline was tested against an 18-worker Cloudflare Workers monorepo that convention-based detection could not see at all. Four public origins, onboarded, deployed and verified over valid TLS.

Three ways in, one place where decisions are made

There are three doors into a LEco machine — a browser, an AI agent over MCP, and a Git push — and exactly one room behind them.

Neither the MCP server nor the CI/CD runner touches Docker. Both act through the dashboard API, so the control token, the lifecycle rules, the destructive-action gates and the audit log live in one place instead of three. If you have ever debugged a platform where the CLI, the UI and the automation each had their own opinion about what “restart” means, you know why this matters.

And every deploy ends where it should: with a real HTTP probe. A deployment that leaves the app returning 502 is recorded as failed, not as deployed. Verification classifies each origin as ok, route_missing, backend_unreachable, tls_invalid or unhealthy — because those need four different fixes, and a bare 502 names none of them.

What actually runs

  • Traefik on 80/443 does TLS termination and Host-rule routing — no more :8080, :3000, :5432 in your head or your bookmarks.
  • *.lh local DNS with mkcert certificates the browser actually trusts.
  • Hosted apps get one slot per repo, including split frontend and /api routes — the same pattern as a production edge.
  • Isolated dev stacks — 30 presets (WordPress, Magento, Laravel, Django, Rails, NestJS, LAMP, MEAN…) and 17 components, each its own Compose project and network, so one client project cannot collide with another.
  • Local AI: Ollama, AirLLM (large models on modest VRAM via layer streaming), Open WebUI on ai.lh, plus n8n and Paperclip for automation and agent orchestration.
  • Cloudflare-local: KV, R2, D1 and Workers-style adapters, so you can exercise bindings without touching production Cloudflare.

Built for agents, not just for people

This is the part I did not expect to matter as much as it does.

LEco ships an MCP server with 65 tools (stdio and streamable HTTP), a Claude Code plugin, and a read-only diagnostician subagent. An agent can check stack health, onboard an application, merge routes, pull a model, read logs and verify hostnames — through the same API the UI uses, with no Docker socket of its own.

The safety model is deliberately boring:

  • Destructive tools (remove, destroy, reinstall, offboard, route strip, model delete) require both confirm=true on the call and LECO_MCP_ALLOW_DESTRUCTIVE=1 on the server. Credential tools are gated separately.
  • Blocked calls report both gates, so the agent surfaces a refusal instead of inventing a workaround.
  • Every tool call is appended to an audit log with argument values passed through a scalar whitelist — the dashboard can answer “which agent touched which application, and when” without ever giving credentials a route into the log.

There is also Ask LEco, retrieval-grounded answering over the platform's own documentation (112 files, 918 heading-aligned chunks) plus live machine state — stack status, app snapshots, Traefik routes, logs — pulled only when the question calls for it. Answers cite their sources, secrets are scrubbed at index time and again from live state, and tests plant a fake key and assert it never reaches a prompt.

Everything in one MIT-licensed repo

It does not stop at the laptop

deployment_mode, base_domain and tls.mode are first-class inputs, not hardcoded assumptions. The same platform installs on a Linux VM with your real domain and ACME, Cloudflare, or static certificates — a preproduction environment for teams who do not want Kubernetes to be the price of entry.

Push-to-deploy comes with it: HMAC-signed GitHub/GitLab webhooks run pull → build hook → deploy → verify → record, with per-step logs, branch filtering, one run at a time per pipeline, and rollback to the previously deployed commit.

One honest caveat, because I would rather say it than have you discover it: the defaults are tuned for a laptop. Before you expose LEco on a public host, read docs/PRODUCTION_HARDENING.md — we wrote it as an audit of our own defaults, including the ones that were wrong, and it tells you exactly what to change.

The difference on day one

Principles we keep coming back to

  1. Evidence over invention. If we cannot prove a port, a hostname, or a service boundary from a named file, we ask instead of guessing.
  2. One control plane. Every entry point acts through the same API, so safety rules cannot be bypassed by picking a different door.
  3. Nothing written into your repository. Your source tree is an input, not a hostage.
  4. Verify, don't assume. A deploy is not done until an HTTP probe says so.
  5. Say what is not true yet. Clients we have not tested are marked untested. Known-weak defaults are documented, not hidden.

Start in minutes

git clone https://github.com/leco-devops/local-ecosystem.git
cd local-ecosystem
./ecosystem-stack/install-foundation.sh
./ecosystem-stack/ecosystem-stack.sh start

Then open http://dashboard.lh and register your first app — or let an agent do it for you.

If you run more than two applications on one machine, or you have ever lost an afternoon to a port map, I would genuinely like your issues and pull requests. The roadmap belongs to whoever shows up.

LEco and project-atlas work hand in hand

These two are halves of the same loop, and I run them together every day.

project-atlas makes a repository legible to an agent. It indexes the markdown you already have, detects rot mechanically — dead links, forked documents, architecture pages citing source files that have all changed since, orphan pages, SOPs past their review date — and generates a searchable knowledgebase, a dashboard, a health report and an agent knowledge graph. Your markdown stays the source of truth, and everything it produces regenerates byte-identically, so the output cannot fork from your docs.

LEco DevOps makes the machine operable by that same agent. 65 MCP tools, one control plane, ports taken from evidence, and a verify step that proves the hostname actually answers.

Put them together and the loop closes: the agent reads documentation it can trust, then acts on infrastructure that refuses to guess.

No stale README. No invented port. No “ask Priya about the ports.” A coding agent can go from a fresh clone to a deployed, TLS-verified hostname on its own, without a human stitching the two halves together at every step. Both are MIT, and both ship a Claude Code plugin and an MCP server, so it is one agent session rather than a toolchain you have to assemble.
